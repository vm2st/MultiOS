# MultiOS 0.35 — защита транзакций и контрактов модулей

`0.35-dev-txguard` — неопубликованная разработка. Не стабильный Release 1.0.

## Что изменилось

### Отказ записи нельзя превратить в успешный commit

Раньше модуль мог проигнорировать отказ undo-журнала из-за исчерпания бюджета,
вернуть успех и зафиксировать уже записанную часть операции. Это воспроизведено
отдельным регрессионным тестом до исправления.

Теперь первая логическая ошибка записи в принадлежащей текущему процессу
активной транзакции переводит её в состояние **только отмена** (abort-only).
Последующие записи и commit возвращают первую ошибку, не продолжая запись.
Восстановление возвращает исходные секторы; после успешного восстановления
можно начать новую транзакцию. Ошибка физического ввода-вывода по-прежнему
требует повторного открытия и восстановления, а не слепого продолжения.
Неактивный или не принадлежащий текущему экземпляру журнал нельзя записывать.
Формат дискового журнала не изменён.

### Драйверы не могут возвращать произвольный «успех»

Обычные операции модулей должны возвращать ровно 0 при успехе или отрицательную
ошибку. Положительные результаты больше не считаются успехом: транзакционная
операция отменяется, нетранзакционный небезопасный результат блокирует том.
Это относится к записи файлов, потоков, ссылкам и операциям чтения.

Монтирование проверяет тип файловой системы, запрошенные границы раздела
и отсутствие отравленного состояния тома. Перечисление каталогов и потоков
допускает только 0 (конец), 1 (элемент) или отрицательную ошибку; при выдаче
элемента курсор обязан строго продвинуться. Это останавливает зацикливание
из-за ошибочного модуля. Чтение, получение корня и перечисление не обращаются
к размонтированному тому. HAL принимает только writable=0 или writable=1.

ABI модулей остаётся версии 5. Двоичная структура таблицы драйвера не изменена,
но собственные адаптеры необходимо сверить с уточнённым контрактом
`include/multios/fs_driver.h`. Курсор перечисления должен быть монотонным.

### Повторяемый большой набор проверок

```sh
python3 tools/check_filesystems.py
```

Сценарий объединяет проверки ядра транзакций, VFS и HAL, санитарные сборки,
настоящие FAT32/exFAT/NTFS-образы, случайный доступ, поэтапное копирование,
NTFS-потоки и выбранные отказы записи, затем сборки BIOS и UEFI.
Отчёт находится в `build/fs-check/results.json`, подробности — рядом в логах.
Ошибка, тайм-аут или отсутствие обязательной зависимости дают ненулевой код,
а не скрытый PASS. `--quick` пропускает длинные матрицы и не заменяет полный прогон.
Проверки загрузки выполняются отдельно.

Добавлен `.github/workflows/filesystems.yml`: он запускает этот сценарий
при push/pull request и вручную, сохраняет отчёт даже при ошибке.
Успешность GitHub Actions подтверждается только реальным запуском в репозитории;
локальный прогон не является подтверждением удалённого CI.

## Сборка и использование

Нужны C-компилятор, make, binutils, Python 3, поддержка сборки i386,
ASan/UBSan, dosfstools, exfatprogs, mtools и NTFS-3G/ntfsprogs.
GNU-EFI и исходники файловых движков входят в поставку. В Ubuntu зависимости
перечислены в GitHub workflow; названия пакетов в других дистрибутивах отличаются.

```sh
make bios-rw
make -j4 FS_PROFILE=profiles/filesystems-ntfs3g.mk uefi
```

В полном комплекте находятся три альтернативных USB-образа с FAT32, exFAT
или NTFS как разделом данных. Каждый содержит BIOS i386-компоненты,
UEFI x64-компонент и FAT32-загрузочный раздел. Это не три раздела данных в одном
образе. Включение записи в консоли: `unlock YES`, выключение: `lock`.
Не используйте экспериментальную запись на единственной копии важных данных.

Для редактирования распакуйте `MultiOS-0.35-FULL-SOURCES.zip`, работайте в
каталоге `MultiOS/`. Исходники драйверов находятся в `drivers/`, HAL — в
`include/multios/hal.h`, профили — в `profiles/`, тесты — в `tests/`.
Настройки готового образа находятся в `EASY/SETTINGS.INI`; применять их нужно
штатными инструментами из исходников на выключенной копии образа.
Изменения C-кода требуют пересборки, а не только замены конфигурации.

Для обновления подготовленного образа используется установщик на копию:

```sh
python3 tools/build_bios_rw_image.py old.img new.img --efi build/BOOTX64.EFI
```

Он устанавливает текущий BIOS bundle из `build/bios-rw/`, обновляет его сырой
загрузочный дубль, EFI и снимок исходников. Целевой файл должен быть новым.
Установщик восстанавливает настройки профиля по умолчанию: сохраните свои
настройки отдельно. Это не интерактивный установщик на физический диск.
Ручная замена только `KERNEL32.BIN` не обновляет сырой BIOS-дубль.

## Что ещё не объявляется готовым

- RW FAT32/exFAT/NTFS остаётся экспериментальным; undo-бюджет конечен.
- Неподготовленные и опасные тома не разблокируются; dirty/hibernated NTFS
  нельзя принудительно объявлять безопасным.
- Не реализована полная Windows-семантика ACL, EFS, reparse и `$LogFile`.
- UEFI использует Boot Services; это не готовый нативный x64-драйверный слой
  после ExitBootServices. Нативный xHCI/UAS этим патчем не добавлен.
- Проверки образов и моделей не сертифицируют реальные USB-контроллеры,
  отключение питания и каждую модель процессора.
