# MultiOS 0.28-dev-usb-hardening / MultiPulti

Неопубликованная разработка. Не стабильный Release 1.0. Этот документ описывает текущий расширенный BIOS-профиль; документы 0.27 и старше — история.

## Что действительно добавлено

Нативный путь: UHCI / OHCI / EHCI → USB Mass Storage Bulk-Only Transport → SCSI → блочный HAL → существующие FAT32, exFAT и NTFS-3G. Linux, Windows и их драйверы во время работы BIOS-ядра не используются. Ядро написано на C с архитектурными ASM-фрагментами. NTFS-3G и FatFs включены с сохранением лицензий.

| Путь | Чтение | Запись | Основание |
| --- | --- | --- | --- |
| BIOS + UHCI/OHCI/EHCI + поддержанный USB BOT диск | Да | Экспериментальная, после `unlock YES` | Новый нативный драйвер 0.28 |
| BIOS + ATA PIO | Да | Экспериментальная, после `unlock YES` | Сохранённый драйвер, отдельный профиль |
| UEFI x64 | Да | Экспериментальная, после `unlock YES` | Сохранённый firmware Block I/O путь; EFI-бинарник из 0.26 |

Все три готовых образа содержат FAT32-загрузочный раздел, раздел DATA выбранной ФС и служебный private undo-раздел. Это не означает возможность одновременно смонтировать любые подключённые тома: системный том выбирается при загрузке.

### Изменения 0.28

1. **UHCI, короткие IN-пакеты.** Short Packet Detect; передача завершается на первом коротком пакете, а не ждёт неисполненные TD. Фактическая длина и DATA toggle считаются по завершённому префиксу, включая нулевой пакет. Следующий CSW не должен читаться как продолжение данных.
2. **OHCI, bulk TD.** Одна general TD на передачу до 512 байт; IN buffer rounding. Длину определяет CurrentBufferPointer, toggle — carry ED. Короткий пакет завершает data phase без запуска следующей data TD. После SKIP перед повторным использованием DMA наблюдаются два реальных OHCI-кадра; неподвижный счётчик приводит к остановке контроллера. Одна задержка PIT больше не считается подтверждением продвижения USB.
3. **EHCI.** Отдельно распознаётся halted-only endpoint; прочие ошибки не превращаются в STALL. Учитываются оставшиеся байты и возвращённый DATA toggle. Перед переиспользованием QH/qTD asynchronous schedule выключается с подтверждением контроллера.
4. **Общий BOT/SCSI.** Код STALL отделён от таймаута/извлечения. В data phase очищается halt нужного endpoint, затем проверяется CSW. Для первого STALL чтения CSW — CLEAR_FEATURE(ENDPOINT_HALT) и ровно один повтор чтения CSW. CBW, WRITE(10) и data phase записи автоматически не повторяются. Проверки signature/tag/residue/status/actual не ослаблены.
5. **Готовность носителя.** До четырёх TEST UNIT READY на старте, REQUEST SENSE после штатного command-failed, до трёх пауз по 100 мс. Транспортная ошибка прекращает попытки. Нет бесконечного ожидания и повторного запуска записи.
6. **NTFS, кеш чтения.** 512 секторов в 128 наборах по четыре позиции. Статический ограниченный кеш только для read-only представлений NTFS, без write-back. Сбрасывается перед writable view, полным mount и при ошибках. HAL, секторный undo и проверка физической записи остаются некешированными. Требуется эксклюзивное владение смонтированным томом: внешнее изменение образа во время работы не поддерживается.
7. **NTFS, отложенные ошибки.** После закрытия тома проверяется не только результат NTFS-3G, но и сохранённая ошибка блочного ввода-вывода. Первая ошибка сохраняется: последующие отказы не подменяют, например, NOSPACE общим IO. После отказа adapter прекращает дальнейший ввод-вывод текущего представления. Ошибка не теряется при reset/remount; незавершённая операция уходит в секторный откат. Тест исчерпания журнала печатает точную диагностику при отказе проверки.
8. **ABI BIOS NTFS runtime.** Явные объявления `ffs`, `mpntfs_strdup`, `strerror`; сборка отклоняет неявные объявления функций и преобразование `int` в указатель. Это не отключение предупреждений. Предупреждения vendor packed fields и RWX LOAD segment пока остаются.
9. **Стартовый счётчик кадров OHCI.** Вместо одного сравнения через 3 мс — ограниченное ожидание трёх наблюдаемых USB-кадров, не более 100 опросов с задержкой 1 мс. Контроллер с неподвижным счётчиком отвергается. Это устраняет обнаруженный ложный отказ запуска OHCI на границе таймеров эмулятора.
10. **Новые тесты.** Реальные bulk-функции трёх HCD проверяются на моделируемых DMA/регистрах: полная, короткая и нулевая передача, STALL, частичный STALL, ошибка, таймаут, извлечение. BOT — отдельные проверки CLEAR_HALT, ограничений повторов и готовности. Кеш — 100000 случайных чтений, вытеснение, смена эпохи, ошибки и переполнение счётчика.

Сохранено из 0.27: BIOS EDD USB boot без ATA; boot MBR-ID guard; проверенный диапазон образа на более крупной флешке; `bios_disk=usb-bot|ata`; начальный RO, явный `unlock YES`, private undo, sticky failure после отказа выбранного диска. Системный USB-диск нельзя переподключить на лету: требуется перезапуск и штатная проверка/восстановление.

Файловые движки не объявлены полными: транспорт использует существующие backend, а изменения NTFS описаны выше. FAT32 не получает файлы размером 4 ГиБ и больше. Для NTFS не обещается реализация всей семантики Windows, всех reparse/ACL/EFS/сжатых/зашифрованных сценариев; см. файловые документы и ограничения конкретного backend.

## Первый запуск

1. Скопируйте нужные данные с флешки в другое место. Побайтовая запись образа заменяет таблицу разделов и данные в диапазоне образа; не считайте оставшийся хвост резервной копией.
2. Выберите `images/MultiOS-0.28-usb-fat32.img`, `-exfat.img` или `-ntfs.img`. Начните с FAT32 на расходной флешке.
3. Запишите raw `.img` через Rufus в режиме DD либо другое средство побайтовой записи. Это не ISO, не обычное копирование файла на флешку и не установщик Windows. Не выбирайте внутренний диск по ошибке.
4. Безопасно извлеките устройство и выберите его в Boot Menu. Для собственного нативного USB-пути нужен BIOS/CSM с EDD и UHCI/OHCI/EHCI. Для UEFI x64 работает прежний прошивочный путь. Неподписанная загрузка не совместима с обычным включённым Secure Boot без собственной доверенной подписи.
5. Проверьте:

```text
ver
modules
usb
fs
```

В BIOS USB-профиле ожидаются `block: pc-usb-bot` и `USB BOT disk ready / RW capable`. Сначала том остаётся RO. Команды с записью выполняйте только на копиях:

```text
unlock YES
mkdir DEMO
write DEMO/HELLO.TXT "Hello USB"
type DEMO/HELLO.TXT
append DEMO/HELLO.TXT "MultiOS"
copy DEMO/HELLO.TXT COPY.TXT
cmp DEMO/HELLO.TXT COPY.TXT
resize COPY.TXT 64
writeat COPY.TXT 0 "TEST"
readat COPY.TXT 0 4
sync
lock
```

`write` и `append` добавляют перевод строки; точное поведение других команд смотрите в `help` и файловой документации. Не извлекайте системную флешку во время работы: после `sync`/`lock` завершите систему. После ошибки сохраните копию всего образа для диагностики; не стирайте служебный журнал ради обхода отказа.

Поддержанная Boot-клавиатура работает через имеющийся USB/PS2 провайдер. OSK: `osk on` / `osk off`, F2 или Ctrl+O; F6 — следующий символ, F7 — выбрать, F5 — предыдущий при третьей кнопке. Физические две кнопки на своей плате требуют адаптера событий NEXT/SELECT, сами GPIO не определяются автоматически. На одном host-контроллере сейчас выбирается только одно устройство (клавиатура ИЛИ диск); для обоих нужны разные поддержанные контроллеры либо другой ввод. Разные root-порты одного контроллера это ограничение не снимают.

## Запуск в QEMU без физической флешки

Сначала создайте расходную копию образа, например `Test.img`. В QEMU, содержащем классические USB host-модели:

```sh
qemu-system-i386 -machine pc -cpu 486 -m 64M \
  -drive file=Test.img,format=raw,if=none,id=stick \
  -device usb-ehci,id=store \
  -device usb-storage,drive=stick,bus=store.0,bootindex=1 \
  -device piix3-usb-uhci,id=input \
  -device usb-kbd,bus=input.0,usb_version=1
```

Здесь ATA-диска нет: системный диск — EHCI USB, клавиатура — отдельный UHCI. Не подключайте один изменяемый образ к нескольким VM одновременно. Для проверки OHCI/UHCI-накопителя замените только `usb-ehci,id=store` на `pci-ohci,id=store` либо `piix3-usb-uhci,id=store`. Самостоятельные контроллеры отличаются от реальных companion-топологий. Проверенная версия эмулятора — QEMU 9.2; некоторые новые/урезанные сборки не содержат нужных моделей. Устройство можно проверить через `qemu-system-i386 -device help`.

## Изменение настроек

На другом компьютере нужен Python 3.9+; для GUI также Tkinter. Выключите VM и работайте с файлом-копией, не физическим диском:

```sh
python3 tools/customize.py --gui
python3 tools/customize.py images/MultiOS-0.28-usb-fat32.img
python3 tools/customize.py images/MultiOS-0.28-usb-fat32.img --settings tools/ATA.INI --output MultiOS-ATA.img
python3 tools/customize.py images/MultiOS-0.28-usb-fat32.img --settings tools/USB-RO.INI --output MultiOS-USB-RO.img
```

Начальный USB-профиль:

```ini
osk=off
bios_input=auto
storage=guarded
bios_disk=usb-bot
```

- `storage=readonly` — принудительный RO, `unlock` его не обходит.
- `storage=guarded` — запись только после явного разрешения и проверок существующего transaction layer.
- `bios_disk=ata` — нативный ATA-диск для BIOS, например IDE primary master VM; USB-клавиатуры при `auto` сохраняются.
- `bios_input=ps2-only` — не читает USB-клавиатуру. При `bios_disk=usb-bot` USB-стек всё равно необходим для диска и запускается явно.
- `bios_input=usb-only` — требует поддержанную USB-клавиатуру, не является универсальным резервным вводом. Не включайте, если единственный USB host уже занят системным диском.

Редактор создаёт НОВЫЙ файл и синхронизирует INI, BIOS/UEFI-профили и CRC-слот BIOS. Изменение одного INI внутри образа обычным архиватором этого не делает. После изменения файла `.img` флешку нужно записать заново. Не расширяйте/перемещайте разделы и не форматируйте служебный 0xDA-раздел.

### Один образ, но три варианта DATA

Каждый `.img` самодостаточен. Выбирайте один, а не записывайте три последовательно. Разные файлы нужны для выбора FAT32/exFAT/NTFS, не для совместной загрузки. В образе есть `SOURCES/PORTING.ZIP`, текущая инструкция `START.TXT` и `DOCS/USB28.MD`. Драйверы пока статические C-модули: выбор уже встроенного — настройкой, изменение реализации — пересборкой. Динамическая загрузка/выгрузка драйверов не реализована.

## Сборка и установка изменённых исходников

Исходники находятся в `MultiOS-0.28-FULL-SOURCES.zip`. На Linux нужны Python3, GCC с i386 code generation, binutils, make, mtools и средства соответствующих ФС. Точная лицензия объединённого ядра с NTFS-3G — GPL-2.0-or-later; MIT-части и лицензии vendor не удаляются.

```sh
cd MultiOS
make bios-rw
python3 tools/build_bios_rw_image.py ../images/MultiOS-0.28-usb-fat32.img ../rebuilt-ata.img
python3 tools/customize.py ../rebuilt-ata.img --settings ../tools/USB.INI --output ../rebuilt-usb.img
```

Пути предполагают распаковку исходников рядом с `images/` и `tools/`. Installer устанавливает весь BIOS-bundle и обновляет raw-копию ядра, MBR-привязку и source snapshot. По умолчанию он создаёт ATA-профиль; последующая команда выбирает USB. Один `MULTIOS/KERNEL32.BIN`, заменённый вручную, недостаточен. Пакет `bios-bundle/` содержит согласованные готовые MBR/loader/kernel и ELF для отладки; можно передать `--bundle ../bios-bundle`.

UEFI-приложение этим не пересобирается и не превращается в native x64 USB-ядро. Для отдельной сборки UEFI используйте существующие профили/инструкции UEFI и upstream-компонентов. Компактная `make all` — другой диагностический профиль, не замена расширенного BIOS NTFS RW-ядра.

### Где модифицировать

- `drivers/pc-bios/usb*.c`, `uhci.c`, `ohci.c`, `ehci.c` — host/USB/block.
- `include/multios/usb_bot.h`, `lib/usb_bot.c` — независимый от host BOT/SCSI слой.
- `core/hal.c` — общая привязка и запрет записи после отказа выбранного носителя.
- `platform/pc-bios/rw/loader.*` — BIOS EDD, RAM/CRC, вход в ядро.
- `tools/customize.py` — безопасное изменение доступных профилей.
- `profiles/pc-bios.mk`, registry и build script — список статически включённых модулей.
- `tests/usb_bot_test.c`, `usb_enum_test.c`, `usb_storage_qemu.py`, `usb_loader_guards.py` — проверка изменений.

Замена host-драйвера обязана соблюдать lifetime DMA, DATA toggle, точную длину/ошибки, таймауты и реальный flush. Подделывать успешные операции для обхода ошибок нельзя.

## Границы текущей реализации

- Нативный новый путь — BIOS i386+, также x64 CPU в BIOS/CSM; не 8086/286, не IA32 UEFI, не generic bare board без платформенного кода. Нужен BIOS EDD, A20, E820-совместимая RAM 1..30 МиБ; для тестов выделено 64 МиБ.
- UHCI/OHCI full-speed BOT, EHCI high-speed BOT, прямые root-порты. Low-speed storage не поддерживается. Full/low-speed на EHCI требует доступного companion и маршрутизации к нему.
- **Нет xHCI/USB 3.x host, внешних хабов, split transactions, UAS, multi-LUN, мыши/touch/звука/камер/USB-сети/Bluetooth и произвольного HID/NKRO.** Наличие USB 2.0-устройства не помогает, если порт обслуживается только xHCI.
- Одна выбранная MSC LUN0, direct-access, сектор 512 байт, READ CAPACITY(10). Нет 4Kn и READ CAPACITY(16). Устройства за пределами этого capacity формата отвергаются. Логический диапазон HAL не более 128 ГиБ, заводской образ значительно меньше; хвост более крупной флешки не используется. В UEFI новый механизм image-prefix этого патча не добавлен.
- На host выбирается одно устройство. Расширенный профиль резервирует до четырёх host каждого типа; это не гарантия совместимости всех PCI устройств данного класса.
- Конфигурационные дескрипторы ограничены буфером (OHCI/EHCI 512 байт, UHCI 500), выбирается ограниченный интерфейс alt0. Нет полноценного драйвера произвольных composite-устройств.
- Polling, identity-mapped 32-bit coherent DMA; нет IRQ-driven I/O, IOMMU, suspend/resume и BAR выше 4 ГиБ.
- Передача по одному сектору и синхронные операции: особенно NTFS через USB 1.1 может работать очень медленно. Нельзя обещать загрузку за несколько секунд на любом устройстве.
- При выдёргивании/неопределённом результате записи нужен перезапуск и диагностика/восстановление; hot-rebind системного диска не делается.
- Private undo — ограниченная защита целых операций, не полная замена NTFS $LogFile и не абсолютная защита от потери питания. Файлы/операции за пределами бюджета могут быть отклонены. Гибернированные/грязные Windows-тома не следует принудительно открывать для записи.
- Реальное железо, питание USB, USB-сертификация и совместимость с Windows chkdsk не проверялись. Эмуляция и внешние read-only проверки — не доказательство стабильного релиза.
