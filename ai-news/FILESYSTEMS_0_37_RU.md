# MultiOS 0.37 — потеря накопителя и безопасное восстановление

`0.37-dev-mediaguard`, неопубликованная разработка. Не стабильный Release 1.0.

## Что исправлено

До патча уведомление `multi_hal_media_failed(ctx)` отключало writable, но
не запрещало последующий callback flush. На 0.36 воспроизведено: после отказа
выбранного устройства disk_flush возвращал 0 и ещё раз обращался к провайдеру.
Прямой путь storage/undo также должен был учитывать HAL-уведомление, а не только
отрицательный результат самого провайдера.

Теперь действует единый отказ выбранного накопителя:

- HAL блокирует read, write и flush без дальнейших callback к этому устройству.
- Storage блокирует прямые read/write/flush, begin, commit и восстановление
  через прежнюю привязку. Он не пытается откатывать данные на исчезнувшем диске.
- Если провайдер уведомил об отказе внутри read/write/flush, а затем вернул 0,
  ноль не принимается за успех. Это важно и при последней проверке commit.
- Простое `multi_storage_reset()` не снимает HAL-блокировку и не разрешает
  вновь обращаться к накопителю. Нужна явная новая привязка исправного устройства.
- Дисковый undo-журнал не форматируется и не удаляется. Его состояние
  проверяется при свежем открытии до монтирования файловой системы.

При ошибке вблизи точки commit исход операции может быть **неизвестен**.
Нельзя обещать, что файл обязательно остался старым: после открытия журнал
может подтвердить уже зафиксированную операцию. Требование — целое старое либо
целое новое состояние, а не частичная смесь. Перед повтором команды проверьте
фактические данные. Не повторяйте запись автоматически наугад.

## Как действовать пользователю

1. Прекратите операции с файлами после ошибки накопителя.
2. Не сбрасывайте и не форматируйте журнал для устранения ошибки.
3. Сохраните копию образа, если это виртуальная машина и копирование безопасно.
4. После устранения причины выполните явное повторное открытие/перезагрузку.
   Устройство должно быть тем же подготовленным носителем, а не случайной заменой.
5. Дождитесь восстановления до монтирования, затем проверьте результат операции.
6. При повторной ошибке не продолжайте RW и не пытайтесь обходить защиту.

Это не автоматический live-hotplug/rebind менеджер. Защита действует, когда
выбранный драйвер сообщил об отказе; она не обнаруживает все возможные физические
отказы самостоятельно. Диагностика низкого уровня вне текущей HAL-привязки —
ответственность платформенного адаптера.

## Для разработчиков модулей

Существующее `multi_hal_media_failed(block_ctx)` принимает контекст текущего
выбранного устройства, не NULL и не контекст другого диска. Оно не перепривязывает
диски и не переключает USB на ATA. Нативный USB BOT-провайдер уже использует
этот маршрут уведомления; пакет усиливает общие последствия уведомления.

Добавлено:

```c
int multi_hal_media_unavailable(void);
void multi_storage_media_failed(void);
```

Первое — read-only проверка отсутствия привязки/сохраняемого отказа.
Второе — внутреннее уведомление storage со стороны HAL: блокирует старый
экземпляр, не выполняет I/O. Обычный драйвер должен уведомлять через HAL,
чтобы одновременно закрывались транзакционный и нетранзакционный маршруты.
Успешная новая multi_hal_bind сбрасывает HAL-отказ; binding смонтированного
тома по-прежнему запрещён. Физическая доступность и идентичность носителя
должны быть проверены платформой до новой привязки.

ABI структур и формат дискового журнала не меняются. Изменения C требуют
пересборки ядра BIOS и EFI; редактирования BOOT.CFG недостаточно.

## Проверка

```sh
python3 tools/check_filesystems.py
```

Полный сценарий включает новые media-failure/media-rw тесты и санитарные
сборки. Quick-режим не включает длинную матрицу реальных файловых мутаций.
Отчёты — `build/fs-check/results.json` и соседние логи.

Для отдельного запуска новых проверок:

```sh
make -j4 FS_PROFILE=profiles/filesystems-ntfs3g.mk build/fs-media-failure-probe build/fs-media-failure-probe-sanitize build/fs-media-rw-probe build/fs-media-rw-probe-sanitize
MULTIOS_PATH_PROBE="$PWD/build/fs-media-failure-probe" python3 tests/path_safety.py
MULTIOS_PATH_PROBE="$PWD/build/fs-media-failure-probe-sanitize" python3 tests/path_safety.py
python3 tests/media_rw.py
MULTIOS_MEDIA_RW_PROBE="$PWD/build/fs-media-rw-probe-sanitize" python3 tests/media_rw.py
```

Нужны make, C-компилятор, Python 3, ASan/UBSan, dosfstools, exfatprogs,
mtools и NTFS-3G/ntfsprogs. Все сценарии используют временные файлы-образы,
не физические диски. Новые тесты уведомлений не являются реальным извлечением
USB, симуляцией всех состояний контроллера или физического отключения питания.

## Сборка и образы

```sh
make bios-rw
make -j4 FS_PROFILE=profiles/filesystems-ntfs3g.mk uefi
```

В комплекте три альтернативных образа: FAT32, exFAT или NTFS как раздел данных.
Каждый содержит BIOS i386 и UEFI x64. Для разработки распакуйте FULL-SOURCES.zip
и перейдите в MultiOS/. Отдельный patch нужен только для исходников 0.36.
Подготовленный образ обновляется на НОВУЮ копию:

```sh
python3 tools/build_bios_rw_image.py old.img new.img --efi build/BOOTX64.EFI
```

Текущий BIOS bundle берётся из build/bios-rw/. Обновляются EFI, исходники
и сырой BIOS-дубль; настройки профиля возвращаются к штатным. Сохраните свои
настройки отдельно. Замена только KERNEL32.BIN не обновляет сырой дубль.
Для первого запуска используйте копию в VM. Запись образа на флешку стирает
прежнее содержимое флешки; внимательно проверяйте выбранное устройство.
`unlock YES` включает экспериментальный RW подготовленного тома, `lock` выключает.

## Что остаётся открытым

RW остаётся экспериментальным на FAT32/exFAT/NTFS. Undo-бюджет конечен;
полная Windows-семантика NTFS ACL/EFS/reparse/$LogFile не реализована.
Dirty/hibernated NTFS не считается безопасным для записи. UEFI использует
Boot Services; нативные xHCI/UAS и универсальная горячая замена не добавлены.
Реальное оборудование и питание требуют отдельной приёмки. TODO.md не закрывается
только количеством моделей и эмуляторных тестов.
