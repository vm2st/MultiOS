# MultiOS 0.36 — отказ ввода-вывода запрещает частичный commit

`0.36-dev-ioguard` — неопубликованная разработка, не стабильный Release 1.0.

## Подтверждённое исправление

В 0.35 запись через корректный HAL могла записать часть операции, затем
получить отказ от `disk_write` из-за адреса за пределами устройства либо
NULL-буфера. Если ошибочный файловый модуль игнорировал отказ и возвращал
успех, commit мог завершиться успешно: этот ранний отказ не доходил до undo.
Регрессия воспроизведена до патча: отрицательный результат disk_write,
но результат multi_storage_finish(0) равен 0.

В 0.36 введена общая передача логического отказа в активную undo-транзакцию:

- Некорректные адрес/буфер в HAL read/write переводят текущую транзакцию
  в режим только отмены, даже если накопитель вообще не вызывался.
- Отказы прямого multi_storage_read также сохраняются в транзакции.
- Некорректные запросы multi_undo_read больше не позволяют зафиксировать
  предыдущие записи текущей транзакции.
- Первая ошибка сохраняется: последующие отказы и ложный успех модуля её
  не перезаписывают. Новых прикладных записей после отказа не происходит.
- Откат логического отказа восстанавливает исходные секторы; том размонтируется,
  чтобы модуль не продолжал работу с устаревшими кешами. После повторного
  монтирования на исправном провайдере можно начать новую транзакцию.

Логическая ошибка запроса не равна физической неисправности накопителя.
Она не должна сама ломать провайдер и мешать откату. Физические ошибки по-прежнему
блокируют текущий экземпляр ввода-вывода: требуется повторное открытие и
восстановление, а не слепой повтор записи.

## Flush после отказа провайдера

MultiBlock64 раньше запрещал новые записи после ошибки, но всё ещё мог
вызвать callback flush. Теперь после ошибки read/write/flush этот callback
не вызывается: возвращается READONLY. Это исключает последующий flush через
уже отказавший экземпляр провайдера. Диагностические чтения по-прежнему
допускаются. Новый экземпляр нужен для восстановления.

Это не отменяет уже выполненные накопителем записи и не гарантирует защиту
от лгущего кеша либо самопроизвольного сброса контроллером.

## Для разработчиков портов

Новые функции:

```c
int multi_undo_abort(MultiUndo *journal, int error);
int multi_storage_reject(int error);
```

Они не выполняют дисковый I/O, сохраняют первый отказ только у собственной
активной транзакции. Ноль нормализуется в INVALID, положительный код — в IO;
использовать эти функции как проверку успеха нельзя. Вне активной транзакции
возвращается нормализованный отказ без запуска/форматирования журнала.

Формат образа и дискового undo не меняется, ABI таблиц модулей не меняется.
Изменения C-кода требуют пересборки BIOS-ядра и UEFI-файла. После ошибки
провайдера нельзя использовать flush как способ «снять» отказ.

## Сборка и проверка

Из каталога распакованных исходников `MultiOS/`:

```sh
python3 tools/check_filesystems.py
```

Полный сценарий включает новые проверки HAL, block64, модели undo,
FAT32/exFAT/NTFS, обычные и ASan/UBSan-сборки, USB/BOT/HCD-модели,
random I/O, staged copy, NTFS ADS/hardlinks и BIOS/UEFI-сборки.
`--quick` не заменяет полную матрицу. Загрузка проверяется отдельно.
Отчёт: `build/fs-check/results.json`.

Зависимости и инструкция запуска сохранены в FILESYSTEMS_0_35_RU.md.
Базовые команды сборки:

```sh
make bios-rw
make -j4 FS_PROFILE=profiles/filesystems-ntfs3g.mk uefi
```

Для воспроизведения нового интеграционного сценария:

```sh
make -j4 FS_PROFILE=profiles/filesystems-ntfs3g.mk build/fs-hal-reject-probe build/fs-hal-reject-probe-sanitize
MULTIOS_PATH_PROBE="$PWD/build/fs-hal-reject-probe" python3 tests/path_safety.py
MULTIOS_PATH_PROBE="$PWD/build/fs-hal-reject-probe-sanitize" python3 tests/path_safety.py
```

Тесты работают с одноразовыми файлами-образами, не с физическими дисками.
Для GitHub добавленный ранее workflow автоматически запускает расширенный
сценарий; фактический статус Actions нужно смотреть в самом репозитории.

## Готовые образы и исходники

Полный комплект содержит три альтернативных образа с FAT32, exFAT или NTFS
как разделом данных. В каждом — BIOS i386-компоненты и UEFI x64-компонент.
Исходники распаковываются в `MultiOS/`. Отдельный patch применяется только
к исходникам 0.35; пользователям полного архива применять его не нужно.

Сначала работайте с копией в виртуальной машине. `unlock YES` включает
экспериментальную запись на подготовленном томе, `lock` выключает её.
При ошибке не продолжайте изменять файлы: сохраните образ, повторно откройте
устройство/перезагрузитесь для восстановления. Не форматируйте журнал для
устранения ошибки: это уничтожает данные отката.

Подготовленный образ обновляется на НОВУЮ копию:

```sh
python3 tools/build_bios_rw_image.py old.img new.img --efi build/BOOTX64.EFI
```

Команда устанавливает текущий bundle из build/bios-rw, EFI и исходники.
Настройки профиля сбрасываются к штатным; сохраните свои настройки отдельно.
Ручная замена только KERNEL32.BIN не обновляет сырой BIOS-дубль.
Запись образа на флешку уничтожает её прежнее содержимое.

## Оставшиеся ограничения

RW всех трёх ФС остаётся экспериментальным. Undo конечен (до 4096 секторов
в штатных новых образах). Полная Windows-семантика NTFS ACL/EFS/reparse/$LogFile
не реализована. Dirty/hibernated NTFS не считается безопасным для записи.
UEFI использует Boot Services. Нативный xHCI/UAS этим пакетом не добавлен.
Проверка в эмуляторе не заменяет реальное питание, контроллеры и матрицу ПК.
Готовность Release 1.0 определяется всем TODO.md, а не числом пройденных тестов.
