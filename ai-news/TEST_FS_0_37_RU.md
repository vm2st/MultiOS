# MultiOS 0.37 — проверка RW при потере устройства

`0.37-dev-mediaguard`, неопубликованная разработка. **Полный локальный software
gate PASS: 18 этапов.** Реальное оборудование и удалённый GitHub Actions
не проверялись. Это не стабильный Release 1.0.

## Воспроизведение до исправления

На исходниках 0.36 новый тест показал:

```text
flush after selected-media failure=0 callbacks=1 (must fail without callback)
```

После уведомления HAL об отказе выбранного устройства flush всё ещё вызывал
провайдера и возвращал успех. Лог ожидаемого провала старой версии находится
в reports/repro-before.log. Это доказательство исходной проблемы, а не провал
окончательного проверочного набора.

## Новые проверки HAL и storage

- После уведомления блокируются read/write/flush, прямой storage I/O,
  begin/finish/prepare через старую привязку; callback-счётчики не растут.
- Уведомление внутри read/write/flush не может быть скрыто последующим 0
  от провайдера. Проверены нетранзакционный HAL и транзакционный путь.
- Сброс multi_storage_reset не снимает HAL-level отказ и не разрешает новое I/O.
- Только явная новая привязка исправного провайдера открывает путь восстановления.
  Проверены повторы отказов во время открытия и самого восстановления.

На каждом образе FAT32/exFAT/NTFS проверены 90 позиций/режимов отказа транзакции
и 66 позиций/режимов открытия/восстановления. Всего **468 комбинаций фикстур**.
Это двухсекторные raw-транзакции через HAL/storage, а не 468 разных файловых
операций. Сигнал вводился до/после callback с намеренно ложным успешным результатом.
После повторного открытия проверялось целое старое либо целое новое состояние,
никогда смесь; для восстановления ACTIVE требовалось исходное состояние.
Тестовые сектора возвращались к оригиналу до дальнейшей проверки самой ФС.
Затем проверена обычная запись и чтение KEEP.TXT через файловый слой.

## Настоящие файловые операции

Дополнительно на трёх ФС проверены **226 выбранных комбинаций** уведомления
до/после сырых записей при выполнении fs_write64 и fs_resize64. Здесь изменялся
настоящий DATA.BIN, а не только raw-секторы модели.

Для каждой комбинации:

1. Мутация завершается ошибкой, том запрещает RW и размонтирован.
2. Нет дальнейших callback после уведомления.
3. Образ повторно открывается, журнал проверяется/восстанавливается до монтирования.
4. Содержимое и размер DATA.BIN соответствуют целому старому или целому новому
   варианту; для роста проверяется нулевая расширенная область.
5. В свежем исправном сеансе успешно создаётся RECOVER.TXT.
6. Выполняется внешний базовый checker; FAT32/NTFS дополнительно читаются
   независимыми mtype/ntfscat с побайтной проверкой ожидаемых вариантов.

Оба новых набора повторены обычной и ASan/UBSan-сборками. Санитарный повтор не
удваивает количество уникальных комбинаций. Это модели уведомлений провайдера,
а не реальная горячая замена USB, не новая эмуляция USB-контроллера и не полная
матрица физического отключения питания.

## Готовые образы

Три образа 0.37 загрузились в QEMU Q35 + OVMF. Проверены версия, пять отказов
опасным именам, write/copy/resize/write-at, сравнение файлов, выключение и
сохранённые байты. Использовались временные копии образов поставки.

USB-диск и клавиатура предоставлены прошивкой через эмулированный xHCI. Это не
подтверждение нативного xHCI MultiOS. UEFI сохраняет Boot Services.
BIOS собран, но не проверен загрузкой: доступная сборка QEMU не содержит
требуемого PC/IDE-профиля существующего BIOS-теста. Для BIOS не выставлен PASS загрузки.

## Повторение

```sh
python3 tools/check_filesystems.py
make -j4 FS_PROFILE=profiles/filesystems-ntfs3g.mk build/fs-read-probe
MULTIOS_BOOT_MODES=uefi python3 tests/fs_path_boot.py PATH_TO_IMAGES
```

Для загрузки нужны QEMU и OVMF; при необходимости задайте OVMF_CODE и OVMF_VARS.
Новые отдельные тесты описаны в FILESYSTEMS_0_37_RU.md. После окончательного
усиления HAL latch выполнен полный повторный прогон; reports/results.json
и логи относятся к нему. Внутренние пути в отчётах заменены нейтральными.
