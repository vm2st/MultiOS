# MultiOS 0.19-dev-stagedfs — большие проверяемые копии

MultiPulti · vm2 studios · t.me/v2vproj. **НЕОПУБЛИКОВАННАЯ РАЗРАБОТКА, не Release 1.0.**

## Что исправлено

В 0.18 копирование целиком помещалось в одну undo-транзакцию: даже при достаточном свободном месте файл больше бюджета операции скопировать было нельзя. В 0.19 `COPY` в transactional-профиле работает через временный файл:

1. Проверяет источник, конечное имя и родительский каталог. Существующий конечный файл НЕ перезаписывается.
2. Создаёт отдельный `MCxxxxxx.TMP` в том же каталоге.
3. Дописывает данные блоками 8192 байт, каждый — отдельная защищённая undo-транзакция. Старые файловые views после каждой мутации заменяются новыми.
4. Сравнивает **все байты** готовой временной копии с источником.
5. Переименовывает её в конечное имя отдельной защищённой транзакцией.

Таким образом размер копии больше не ограничен размером ОДНОЙ транзакции. Ограничения самой ФС, доступного места, поддерживаемой геометрии/аудита и каждой отдельной операции остаются. Сложная метаоперация тоже может не поместиться в журнал. Нет фоновых писателей/параллельного доступа к тому же диску.

**Это копирование данных, не полное клонирование файла NTFS:** ACL, ADS, timestamps, hardlink relationships и sparse allocation layout не переносятся. Разреженный файл может занять полный логический размер на destination. Сжатие определяется целевым каталогом/драйвером, а не клонированием атрибутов источника.

Отдельно защищены совпадение временного имени с конечным именем и попытка продолжения через регистровый/8.3-алиас самого источника, включая пустые FAT-файлы с first cluster = 0.

Дополнительно `CRC32` и `CMP` используют 64-битные VFS views, а не старые 32-битные Stream-размеры. Старый ошибочный текст «max 128 sectors» в списке драйверов исправлен: бюджет определяется подготовленным образом.

## Исправление загрузочного сбоя NTFS

Проверка в UEFI обнаружила реальную причину остановки на конце каталога: системный GCC по умолчанию выбирал `x86-64-v2` и вставлял `PMINSD` (SSE4.1). На базовом x64 это вызывает invalid-opcode exception. Теперь весь собственный EFI-код и NTFS-3G явно собираются с `-march=x86-64`, а не с неявными настройками дистрибутива.

Дополнительно в установленной системной GNU-EFI найдена `BLENDVPS` (SSE4.1). Поэтому **по умолчанию GNU-EFI 3.0.11 пересобирается из включённого архива** с тем же baseline ISA. Не полагаемся на случайную совместимость системного `libefi.a`. Добавлены supplemental ISA audit и воспроизводимый QEMU `qemu64` boot-тест. Это исправление совместимости, не обещание работы на любом устройстве.

## Команды

```text
UNLOCK YES
COPY /SOURCE.BIN /RESULT.BIN
CMP /SOURCE.BIN /RESULT.BIN
CRC32 /RESULT.BIN
LOCK
```

Для управляемой паузы:

```text
UNLOCK YES
COPYPAUSE /SOURCE.BIN /RESULT.BIN 24576
```

Команда останавливается на границе блока, когда скопировано не меньше указанного числа байт, и печатает временный путь. Если порог не меньше размера источника, копирование завершается обычно. Нулевой порог запрещён. Это явно запрошенная пауза; универсального неблокирующего Ctrl+C в текущем HAL нет.

Для продолжения используйте **фактически напечатанное имя** (пример):

```text
COPYRESUME /SOURCE.BIN /RESULT.BIN /MC000001.TMP
```

Временный файл должен быть в том же каталоге, что destination (с тем же написанием родительского пути). Проверяется ВЕСЬ его префикс относительно текущего источника, затем копируется остаток и снова сравнивается весь файл. Неизвестные/несовпадающие временные файлы автоматически не удаляются и не переписываются.

`COPYATOMIC source dest` сохраняет прежнюю операцию «вся копия — одна транзакция». Она ограничена бюджетом журнала. В историческом non-TX профиле обычный COPY остаётся прежним bounded copy, а COPYPAUSE/COPYRESUME не поддерживаются.

## После сбоя

- Не редактируйте работающий VM-диск внешними инструментами.
- После I/O ошибки или пропадания питания сначала переподключите/перезагрузите систему: undo recovery выполняется до RW-доступа. Затем `UNLOCK YES`.
- Проверьте destination: если финальное переименование уже committed, файл может существовать полностью, даже если ответ flush был потерян. Не обещается «всегда ошибка = конечного файла нет».
- Если destination отсутствует, временный файл может содержать проверяемый committed-префикс. Используйте COPYRESUME с исходным источником или явно удалите временный файл после проверки.
- Успешное копирование удаляет временное имя переименованием. После ошибок временный файл намеренно сохраняется; это не утечка без доступного пути.
- Отменяется текущая транзакция, а НЕ весь многошаговый COPY. Уже committed-префикс остаётся. На ошибки нельзя отвечать принудительным снятием защиты тома.

## Готовые образы и запуск

В комплекте три альтернативных raw-образа `images/MultiOS-0.19-dev-stagedfs-{fat32,exfat,ntfs}.img`: BIOS boot/kernel, FAT32 ESP, выбранный data-раздел, приватный undo-раздел на 4096 записей. Не три ФС в одном разделе.

Для первого запуска — FAT32, сохраняемая КОПИЯ образа, x64 UEFI, Secure Boot отключён (EFI не подписан доверенным ключом).

Из `source/MultiOS`:

```sh
python3 tools/run_upstream.py ../../images/MultiOS-0.19-dev-stagedfs-fat32.img
```

Этот launcher работает на ВРЕМЕННОЙ копии, изменения после выхода удаляются. Для постоянных экспериментов подключите отдельную копию образа к VM. VirtualBox:

```sh
VBoxManage convertfromraw MultiOS-0.19-dev-stagedfs-fat32.img MultiOS.vdi --format VDI
```

В образе: `MULTIOS/BOOT.CFG`, `SOURCES/PORTING.ZIP`, `DOCS/FS19.MD`. C-драйверы статические и требуют пересборки. BIOS читает raw-зеркало ядра; нельзя менять только KERNEL32.BIN обычным редактором. Используйте imagectl install или новый образ.

## Пересборка и проверки

Linux/WSL: GCC/binutils/make/Python, dosfstools/mtools/exfatprogs/ntfs-3g tools; QEMU/OVMF для boot-тестов. Полная соответствующая исходная база NTFS-3G и FatFs включена, GNU-EFI source archive включён. В guest не требуется Linux/FUSE/Windows.

Обычная сборка использует включённые исходники GNU-EFI: установленный пакет GNU-EFI не нужен. `tools/build_uefi_runtime.py` создаёт локальный SDK в `build/gnu-efi-sdk`; исходники и лицензии включены. Для сознательного использования системного GNU-EFI задайте `USE_SYSTEM_GNUEFI=1` и подходящие EFIINC/EFILIB/EFIGNUEFILIB/EFICRT; затем обязательно прогоните ISA audit и boot tests. Старые инструкции с `/usr/lib64` относятся к этому опциональному режиму.

```sh
make upstream-image UPSTREAM_DATA_FS=fat32 UPSTREAM_OUTPUT=build/new-fat32.img
make upstream-image UPSTREAM_DATA_FS=exfat UPSTREAM_OUTPUT=build/new-exfat.img
make upstream-image UPSTREAM_DATA_FS=ntfs UPSTREAM_OUTPUT=build/new-ntfs.img
make FS_PROFILE=profiles/filesystems-ntfs3g.mk build/fs-copy-probe build/fs-copy-probe-sanitize
python3 tests/staged_copy.py
MULTIOS_COPY_PROBE="$PWD/build/fs-copy-probe-sanitize" python3 tests/staged_copy.py
MULTIOS_TEST_JOURNAL_RECORDS=128 python3 tests/staged_copy.py
```

Дополнительно:

```sh
make FS_PROFILE=profiles/filesystems-ntfs3g.mk test-uefi-isa
python3 tests/staged_copy_boot.py
```

Второй тест ожидает три готовых образа с именами из этого комплекта в `build/`; проверяет на временных копиях, не на исходных образах. Host-тесты >4 MiB и загрузочные тесты 32769 байт — разные проверки; не выдаются друг за друга.

Sanitizers требуют доступных libasan/libubsan; при необходимости `LD_LIBRARY_PATH`. Итоговые результаты и реальный объём испытаний — `reports/stagedfs-0.19/`, старые отчёты сохраняются как история. Fault-тесты нового COPY выбирают точки raw-write отказа и завершения ПРОЦЕССА; это не исчерпывающий power-cut стенд и не модель всех аппаратных повреждений. Старые детальные undo/FS fault suites — отдельные тесты.

## Что НЕ закончено

- BIOS NTFS всё ещё RO; NTFS RW — host/UEFI. UEFI сохраняет Boot Services, это не самостоятельный x64 kernel после ExitBootServices.
- FAT32/exFAT сохраняют bounded mount/unlock-аудиты геометрии/кластеров/глубины. Наличие upstream FatFs не отменяет этих ограничений.
- 4096 undo-записей ≈2 MiB изменённых данных+метаданных за ОДНУ операцию; большие COPY теперь многооперационные, не стали одной неограниченной атомарной транзакцией.
- Нет полной Windows ACL/security, EFS/BitLocker, всех reparse/ADS-интерфейсов и собственного NTFS $LogFile recovery/chkdsk.
- HAL 512 байт/сектор, до 128 GiB, без GPT/4Kn/RAID и универсальных нативных storage/USB-драйверов.
- Физические power-cut и широкая аппаратная матрица не пройдены. Нужен корректный durable flush от устройства.

Поэтому утверждение «всё полностью закончено и стабильно на каждом устройстве» пока неверно. Не используйте единственную копию важных данных.
