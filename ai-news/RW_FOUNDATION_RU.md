# MultiOS / MultiPulti: основа безопасной записи

**vm2 studios | t.me/v2vproj**  
**Внутренняя разработка. НЕ Release 1.0. НЕ стабильный RW-релиз.**

## Что получено на этом шаге

Добавлен собственный ограниченный секторный undo-журнал на C: `lib/undo.c`, API `include/multios/undo.h`, испытания `tests/undo_test.c`, цель `make test-undo`.

Он хранит исходные секторы до изменения и позволяет восстановить состояние перед незавершённой транзакцией. У журнала два заголовка, поколения, CRC32, привязка к носителю и диапазонам, проверка всех записей до отката. Повторный обрыв восстановления допускает новый запуск восстановления. Ошибка ввода-вывода блокирует продолжение записи через текущий контекст.

**Модуль пока НЕ подключён к драйверам файловых систем и НЕ включён в загрузочный образ.** Он не добавляет ни одной команды файловой записи и не меняет режим монтирования. Намеренно не пересобран и не переименован старый образ под видом новой готовой ОС.

## Реальное состояние файловых систем

| ФС | Состояние после этой работы |
| --- | --- |
| FAT32 | Имеющийся экспериментальный RW не изменён. Журнал к нему ещё не подключён; стабильность при отключении питания не подтверждена. |
| exFAT | Имеющийся экспериментальный RW не изменён. Журнал к нему ещё не подключён; стабильность при отключении питания не подтверждена. |
| NTFS | Существующий ограниченный reader. Writer отсутствует. Полной поддержки RW нет. |

Private undo — не NTFS `$LogFile`, не его replay и не замена логики `$MFT`, `$Bitmap`, `$I30`, `$Secure`, fixup, выделения места и согласованности метаданных. Чтобы объявить NTFS RW, всё это требуется реализовать и проверить отдельно. Включить флаг RW вместо реализации нельзя.

## Модель надёжности и ограничения

- Один писатель, один носитель, один непрерывный защищаемый диапазон; без параллельного доступа и без внешних писателей.
- Только секторы 512 байт. LBA нового API 64-битные; это **не** снимает прежние ограничения адресации всей ОС/ФС.
- От 1 до 128 различных целевых секторов на транзакцию. Ёмкость равна `(journal_sectors - 2) / 2`; допустимый размер резервной области — 4–258 секторов. Повторная запись того же сектора использует одну резервную копию.
- Каждый успешный `flush` провайдера обязан действительно сохранять и упорядочивать все предыдущие записи. Если контроллер/прошивка сообщает успех без сохранения данных, гарантий нет.
- В тестовой модели проверяются потеря несброшенного кэша, разрыв текущей записи, частичное неупорядоченное сохранение и сбой после сохранения до подтверждения. Это не доказательство для любого железа, не полное перечисление всех возможных повреждений и не сертификация накопителей.
- CRC32 выявляет многие повреждения, но не защищает от злоумышленника и не гарантирует обнаружение всех ошибок. `media_id` — метка привязки, не подпись.
- Журнал — обычные бинарные данные в специально зарезервированной области, не редактируемый вручную конфиг. Переносимость драйверов от этого не отменяется.
- Код не ищет свободное место на диске. Резервную область должен назначить создатель образа/BSP вне ВСЕХ разделов, живых ФС, загрузчиков и служебных областей. Проверка конфигурации выявляет пересечение с переданным защищаемым диапазоном, но не знает о других владельцах секторов.
- Не использовать на рабочих дисках. Для разработки — только отдельные одноразовые образы и резервные копии.

## Протокол записи

1. `format` разрешён только для новой, полностью нулевой, заранее выделенной области. При любом ненулевом секторе — `EXISTS` до первой записи. Автоформатирования нет.
2. `open` читает и проверяет зеркала, поколения, привязку, а у ACTIVE-журнала — все записи. Сам ничего не пишет. Непонятный/повреждённый журнал не превращается в пустой.
3. ACTIVE после открытия означает: сначала `recover`, затем монтирование ФС. Нельзя смонтировать её RW и отложить восстановление «на потом».
4. `begin` сохраняет ACTIVE в оба зеркала с отдельным `flush` каждого. Заранее резервируется запас номеров поколений для максимально полной транзакции и завершения.
5. При первом изменении сектора сохраняются исходные 512 байт и дескриптор, выполняется `flush`, затем обновляются оба заголовка с `flush`. Только после этого допускается целевая запись.
6. `commit` повторно проверяет записи журнала, сохраняет целевые данные через `flush`, затем пишет CLEAN в оба зеркала с `flush`.
7. `recover` проверяет ВСЕ записи до первого изменения целевых данных, восстанавливает исходные секторы в обратном порядке, делает `flush`, сохраняет CLEAN. Дескрипторы и данные также проверяются повторно при чтении для восстановления.

Если питание исчезло во время commit, после нового открытия допустимы старое или полностью новое состояние, но в проверенной модели не смесь. Ошибка commit означает **неизвестный результат**, а не обещание «операция точно отменена»: первое CLEAN-зеркало уже могло стать долговечным.

Если достигнут лимит новых секторов, `write` возвращает `NOSPACE` до изменения нового целевого сектора. Предыдущие записи транзакции уже могли изменить носитель. Вызывающий слой должен прервать операцию и откатить её, а не завершить частичную файловую операцию как успешную. Автоматическое разбиение на транзакции не делает большую файловую операцию атомарной.

## Подключение разработчиком — ещё НЕ выполнено

Пример порядка вызовов, не готовый драйвер и не команда для физического диска:

```c
MultiBlock64 block = {0};
MultiUndo undo = {0};
/* provider: проверенные read/write/flush; cfg: отдельно выделенные диапазоны. */
int rc = multi_block64_bind(&block, &provider);
if (rc < 0) return rc;
rc = multi_undo_open(&undo, &block, &cfg);
if (rc < 0) return rc;  /* Не форматировать журнал вместо восстановления! */
rc = multi_undo_recover(&undo);
if (rc < 0) return rc;
/* Только теперь разрешается монтирование поддерживаемой ФС. */
rc = multi_undo_begin(&undo);
if (rc < 0) return rc;
rc = multi_undo_write(&undo, target_lba, full_sector);
if (rc < 0) {
    /* NOSPACE/ошибка аргумента: прекратить операцию и выполнить recover.
     * I/O: остановить доступ, отбросить оба контекста, заново открыть
     * устройство и журнал; восстановить до повторного mount.
     * Не сообщать об успешной файловой операции. */
    return rc;
}
return multi_undo_commit(&undo); /* Ошибка может означать неизвестный результат. */
```

Для полного подключения нужны:

1. Явная безопасная схема размещения журнала в создаваемом образе, стабильная идентификация носителя, версии и политика миграции.
2. Перевод ВСЕХ путей записи ФС, включая FAT/bitmap/директории/флаги/служебные секторы, через общий транзакционный интерфейс. Любой обход уничтожает гарантии.
3. Планирование ёмкости до изменений, согласованность файловых кэшей, их сброс/инвалидация после отката; блокировка конкурентного доступа. `recover` не чинит содержимое кэшей ФС.
4. Выделение атомарных операций, отдельная политика больших файлов, заполнения диска, отмены и сбоев во время расширения директорий.
5. Реализация NTFS writer и отдельной поддержки его системных структур. Частный журнал не следует выдавать за совместимый NTFS transaction log.
6. Испытания именно файловых операций: отказ на каждом write/flush, независимые проверки структуры, холодное повторное монтирование, BIOS/UEFI и реальные контроллеры с выключением питания.

## Сборка и использование исходников

В исходном дереве MultiOS, Linux, компилятор C11/GCC и Make:

```sh
make build/undo-test
./build/undo-test
make test-undo
```

Последняя команда собирает и обычный вариант, и вариант AddressSanitizer + UndefinedBehaviorSanitizer. Для него нужны runtime-библиотеки ASan/UBSan вашего компилятора. Если их нет, установите соответствующие пакеты окружения; не отключайте ошибки и не считайте несостоявшийся запуск пройденным тестом.

Отдельная проверка 32-битного freestanding-объекта:

```sh
cc -std=c11 -Wall -Wextra -Werror -Wno-misleading-indentation \
  -Ilib -Iinclude -m32 -march=i386 -ffreestanding -fno-pie -fno-pic \
  -fno-builtin -Os -c lib/undo.c -o build/undo-i386.o
nm -u build/undo-i386.o
```

Требуется компилятор с генерацией i386. Объект зависит от `mcopy`, `mzero`, `multi_block64_read/write/flush`; это проверка компиляции, не загрузки на реальном i386. Основная ОС НЕ получает модуль автоматически от выполнения `make test-undo`.

В этом комплекте исходники, а не новый загрузочный образ. Для обычной сборки старых целей смотрите существующие инструкции и их зависимости; не считайте прохождение изолированного теста подтверждением всех драйверов или ФС.

## Формат журнала v1 для разработчиков

Little-endian. Первые два сектора — зеркальные заголовки; затем пары «дескриптор, исходный сектор». В CRC32 каждого заголовка/дескриптора входят байты 0–507; CRC хранится в байтах 508–511. Резервные поля обязаны быть нулевыми.

Заголовок: magic `MPUNDO1\0` @0; version @8; sector_bytes @12; header_bytes @16; state @20; sequence u64 @24; transaction u64 @32; count @40; capacity @44; journal_start u64 @48; journal_sectors u64 @56; data_start u64 @64; data_sectors u64 @72; provider_sectors u64 @80; media_id[16] @88; reserved @104. CLEAN=0, ACTIVE=1.

Дескриптор: magic `MPUNDOR1` @0; version @8; index @12; transaction u64 @16; target_lba u64 @24; payload_crc @32; reserved @36; media_id[16] @40; reserved @56. Все не помеченные u64 числовые поля — u32.

Одинаковые поколения зеркал должны быть побайтово одинаковы; различные — соседними. Выбирается более новое валидное зеркало. CRC-валидный заголовок с чужой привязкой не игнорируется ради второго локального. Никакого автоматического «исправления» неизвестного формата нет.

## Политика выпуска

Работа остаётся неопубликованной. Тесты этого модуля не являются основанием объявить Release 1.0 или обещать стабильную запись FAT32/exFAT/NTFS. Следующий обязательный этап — реальная интеграция и файловые fault-тесты, а не смена номера версии.
