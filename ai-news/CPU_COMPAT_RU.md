# MultiPulti 0.6: максимально широкий общий минимум x86/x64

> Текущий снимок: **0.11-dev, не опубликован**. Первая публичная версия — только
> стабильный **Release 1.0**. См. RELEASE_POLICY_RU.md и TWO_BUTTONS_RU.md.

**vm2 studios — t.me/v2vproj.**

## Что сделано

- BIOS kernel остаётся **i386 integer baseline**, без перехода всей системы на
  i686/CMOV, FPU, MMX, SSE/SSE2, AVX, APIC, TSC или обязательный CPUID.
- GCC **и ассемблер** ограничены i386; дополнительный opcode-аудит ищет случайные
  FP/SIMD/CMOV/TSC и некоторые более новые инструкции. Это вспомогательная
  проверка, не формальная верификация полного набора инструкций.
- CPUID выполняется только если EFLAGS.ID действительно изменяем. Без него
  остаётся базовый путь, без попыток угадать модель или вызвать недоступную
  инструкцию. Сам ID bit восстанавливается после проверки.
- `CPU` показывает режим исполнения, vendor, brand, family/model/stepping и
  объявленные возможности. Эти флаги **не включают** SIMD/FPU и не доказывают
  работоспособность инструкций/драйверов. Неизвестный vendor не блокирует запуск.
- Первый тест в MBR использует только 16-битные инструкции: распознаёт отсутствие
  необходимого уровня CPU до 32-битного кода и выводит `i386+ required`.
  Обработка 8086/186/286 проверена по алгоритму/дизассемблированию, не на реальном
  таком процессоре; поддержкой этих CPU это не является.
- Убрано предположение, что у платы есть fast-A20 port 0x92. Нынешние kernel,
  BSS, стек, VGA и рабочие буферы адресуются ниже 1 MiB. При расширении памяти
  потребуется настоящее обнаружение/включение A20 в BSP, а не использование
  памяти выше 1 MiB без проверки. Стек по-прежнему ожидает обычную PC low RAM.

## Что означает поддержка

**i386+ — цель по инструкциям, а не сертификат всех плат.** 8086/8088/186/286
нуждаются в другой 16-битной ветке ядра, которой здесь нет. QEMU используемой
версии не предоставляет достоверной модели 386, поэтому физический 386 и
по-настоящему отсутствующий CPUID пока не проверены. Forced fallback build —
проверка ветки программы, не замена такого оборудования.

На подходящей x64 машине с BIOS/CSM запускается тот же 32-битный kernel. Для
UEFI x64 есть отдельный firmware-hosted target: ABI x86-64, а не «i386 без SSE».
CPU там показывает `Execution: 64-bit`. Native x64 после ExitBootServices,
UEFI IA32 и реальный bare-ROM BSP не появились от добавления CPU-диагностики.

Intel/AMD/vendor string не являются whitelist. Проверка QEMU с искусственным
vendor доказывает лишь отсутствие такого запрета, а не тест VIA/Cyrix/Zhaoxin.

## Матрица проверки

`tests/cpu_matrix.py` загружает один и тот же BIOS kernel, исполняет CPU/VER,
создаёт и читает файл на каждой эмулируемой конфигурации:

486; Pentium; Pentium II; Pentium III; Athlon; Atom n270; Core Duo; Core 2 Duo;
qemu32/qemu64; Phenom; Conroe; Nehalem; Westmere; Sandy Bridge; Ivy Bridge;
Haswell; Broadwell; Skylake-Client; EPYC; неизвестный vendor; ещё два варианта
с выключенными FPU/MMX/SSE/SSE2/CMOV. Итого **23 конфигурации одного бинарника**.

Отдельно загружается сборка с полностью исключённым probe/CPUID кодом на
эмулируемом 486. Она успешно работает с файлами без CPUID. Это другой тестовый
бинарник; он не поставляется как второй .img и не является новой архитектурой.
Модель QEMU и её vendor/family — не физический процессор и не сертификация
производителя; эмулятор может не воспроизводить все аппаратные особенности.

```bash
make test-cpu
QEMU=/path/to/qemu-system-x86_64 make test-cpu-matrix
```

Pure C unit проверяет 10000 вариантов декодирования signature и ошибки
публикации. Host probe unit проверяет восстановление ID и forced-disabled path.
Основные файловые и модульные регрессионные тесты остаются обязательными.

## Диск/плата — отдельная работа

В BIOS по-прежнему используется ATA primary master с MBR-ID guard. **Профиль
BIOS-backed INT 13h/INT 10h/INT 16h из обсуждения ещё не реализован.** Поэтому
сейчас нельзя обещать работу на любом BIOS PC с USB/AHCI/NVMe, даже если CPU
подходит. На UEFI за контроллер отвечает прошивка. Для дальнейшего расширения
реальной совместимости следующий отдельный этап — BIOS service bridge и
firmware-backed block driver, затем дополнительные BSP/native controllers.

## Обновление образа

В 0.6 изменён не только kernel, но и MBR. `make update-unified` теперь обновляет
MBR-код, raw kernel + файловые зеркала, EFI в одной транзакции, сохраняя disk ID,
таблицу разделов, конфигурацию и exFAT-данные. Перед обновлением копия и остановка
VM обязательны. Ручной эквивалент:

```bash
python3 tools/imagectl.py install build/MultiOS-MultiPulti.img \
  --boot build/boot.bin --kernel build/kernel.bin --efi build/BOOTX64.EFI
```

Без `--boot` старый интерфейс допустим, но он **не обновит MBR**. Команда put для
`MULTIOS/BOOT32.BIN` синхронизирует первые 440 байт MBR, не его disk ID/разделы.
Не заменяйте MBR полным сектором другого образа. См. ONE_IMAGE_RU.md.
