# MultiPulti 0.9-dev — первый этап стабилизации ядра

**vm2 studios | t.me/v2vproj · UNPUBLISHED DEVELOPMENT**

Это законченный этап обработки аварий BIOS i386-ветки, а не законченная ОС 1.0.
UEFI остаётся firmware-hosted приложением: обработчики этой главы в неё не
устанавливаются. Список аппаратных драйверов 0.8 не расширился.

## Реализовано

1. После очистки BSS, до запуска модулей, устанавливается собственная IDT из
   256 записей. Обычные исключения/неожиданные векторы идут в fail-stop panic.
2. Assembly stubs нормализуют error code, сохраняют регистры и сегменты,
   очищают DF и передают C-обработчику кадр с проверенными compile-time offsets.
3. Независимая диагностика VGA + COM1: vector/error, EIP/CS/EFLAGS, основные
   регистры, ESP/сегменты; для #PF предусмотрен CR2. Без HAL, heap, файловых
   операций и ожидания клавиатуры. UART имеет программный предел ожидания.
4. Собственная GDT сохраняет selectors 08/10 и добавляет обычный TSS и
   emergency TSS. Для #DF установлен task gate с отдельным стеком 8 KiB.
   В сообщении двойной ошибки выводится состояние прерванной задачи.
5. BIOS C-код собирается с `-fstack-protector-strong` и global canary.
   Canary фиксированный: обнаруживает часть случайных повреждений стека,
   **не является секретом, защитой от эксплуатации или заменой memory isolation**.
   Panic path намеренно собирается без instrumentation, чтобы избежать рекурсии.
6. Panic запрещает maskable interrupts и останавливает CPU (`cli; hlt`).
   Нет автоматического продолжения, перезагрузки или попытки записать журнал на
   возможно повреждённую файловую систему. Legacy PIC замаскирован; IRQ handlers
   и PIC remapping не добавлены. Обычное ядро по-прежнему polling, IF=0.
7. Отдельные TEST-образы генерируют #UD, #DE, #GP, #DF, INT81 и canary failure.
   Они НЕ входят в поставку; production kernel не содержит команд аварийного теста.

## Проверка

```bash
make all uefi multipulti
python3 tests/kernel_guard_audit.py
QEMU=/path/to/legacy-pc-qemu make test-kernel-faults
QEMU=/path/to/legacy-pc-qemu make test
```

`tests/kernel_faults.py` использует CPU 486 и qemu64. Проверяется не только
текст: QMP подтверждает HLT=1 и IF=0, для #DF — TR=0020 и ESP внутри отдельного
стека. SHA-256 диска до/после аварии должен совпасть. Тест canary меняет guard
при живом защищённом кадре: проверяется compiler-generated epilogue, без C
out-of-bounds UB. Это диагностическая инъекция, не доказательство обнаружения
всех видов переполнения. Каждый тест запускается в отдельной VM.

По умолчанию machine=pc. Для изолированных ранних fault tests допустимо
`MULTIOS_TEST_MACHINE=q35`; это не добавляет в ОС драйвер AHCI для Q35.

Отчёты: `build/kernel-fault-report.txt`, `build/kernel-guard-audit-report.txt`,
`build/dev09-regression-report.txt` и другие отчёты с текущим префиксом dev09.
Старые проверки 0.8 не выдаются за новый прогон. Подробные fault logs и регистры
сохранены в `build/kernel-fault-logs/` в поставке.

## Границы, которые нельзя скрывать

- Это обнаружение и аварийная остановка, не recovery и не изоляция процессов.
- Нет paging/guard pages, page allocator, защиты NULL или контроля всех индексов.
- Нет гарантии, что диагностика сработает при произвольном повреждении RAM,
  GDT/IDT/TSS, DMA, самого panic-кода или обоих стеков; triple fault ещё возможен.
- До установки IDT существует раннее окно загрузки; NMI не замаскирован.
- #PF, NMI и machine check не прошли отдельную аппаратную/эмуляционную инъекцию.
- Для #DF отдельный стек проверен; произвольное реальное переполнение основного
  стека и выход за границы памяти этим не сертифицированы.
- UART/VGA могут отсутствовать или зависнуть на конкретной плате; предел цикла
  не гарантирует время при неисправном аппаратном I/O. Fallback renderer для
  устройств без VGA здесь не добавлен.
- Panic не вызывает USB/дисковые драйверы и не гарантирует остановку уже идущего
  DMA или атомарность прерванной exFAT-записи. После аварии образ может требовать
  проверки; нельзя обещать сохранность всех данных.
- CPU baseline остаётся i386 integer. Нет поддержки 8086/286, native x64,
  новых USB-контроллеров или обещания запуска на каждой плате.

Безопасное обнаружение/учёт памяти и IDT-independent recovery boot profile;
широкий дисковый доступ и ошибки I/O; восстановление файловой системы;
OHCI/EHCI/xHCI и проверенный hotplug; физическая матрица железа; воспроизводимая
release candidate сборка. Назвать текущий архив «стабильный Release 1.0» нельзя.
