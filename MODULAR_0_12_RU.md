# Модули MultiOS 0.12-dev

vm2 studios | t.me/v2vproj — модульный шаблон MultiOS / MultiPulti.

## Что действительно модульно

- Переносимое ядро/консоль: `core/`, `lib/`; аппаратные реализации: `drivers/`, `platform/`.
- Аппаратные ABI/реестры: `include/multios/hal.h`, `modules.h`, профили `profiles/pc-bios.mk`, `profiles/uefi.mk` и соответствующие registry.h.
- **Новый файловый ABI:** `include/multios/fs_driver.h`. `lib/fs.c` — маршрутизатор VFS, а не цепочка `if FAT32 / else NTFS`.
- Реестр ФС: `profiles/filesystems.registry.h`; список собираемых реализаций: `profiles/filesystems.mk`.
- `FS DRIVERS` перечисляет включённые модули и возможности записи. Отсутствующий в профиле драйвер не появляется от изменения текстовой подписи.

Это **статическая модульность сборки**. Нет загрузки произвольного ELF/.drv из образа, выгрузки драйвера на ходу, изоляции модулей или совместимости с Windows-драйверами. Образ редактируется без пересборки при изменении данных/настроек или замене уже собранного совместимого бинарного комплекта. Изменение C требует сборки.

## Пример: сборка только с FAT32

Уже включены два файла примера:

```make
# profiles/filesystems-fat32.mk
FS_DRIVERS = lib/fat32.c
FS_REGISTRY = profiles/filesystems-fat32.registry.h
```

```c
/* profiles/filesystems-fat32.registry.h */
&multi_fs_fat32,
```

Сборка:

```sh
make all uefi multipulti FS_PROFILE=profiles/filesystems-fat32.mk
python3 tools/mkunified.py --data-fs fat32 --output build/My-FAT32.img
```

Возврат полного набора:

```sh
make all uefi multipulti FS_PROFILE=profiles/filesystems.mk
```

**Важно:** исторический `build/multios.img`, создаваемый `make all`, содержит exFAT и непригоден как тестовый диск FAT32-only сборки. Используйте новый образ `--data-fs fat32`. Общие тесты `make test` рассчитаны на полный профиль.

Менять профиль во время параллельной сборки нельзя. Make отслеживает профиль/реестр и пересобирает объекты при переключении. Для безопасного переноса ядра и EFI используйте согласованные бинарники одной сборки.

## Собственный драйвер ФС

1. Реализуйте операции над абстрактным блочным устройством, без POSIX/BIOS-вызовов внутри переносимого кода.
2. Экспортируйте `const MultiFsDriver` с `abi=MULTIOS_FS_ABI`, `size=sizeof(MultiFsDriver)`, уникальными `kind` и ASCII `id`.
3. `probe` возвращает 1 только для своей ФС, 0 для чужой, отрицательное значение для ошибки. Два совпадения — отказ, не случайный выбор. Не принимайте NTFS за FAT32 из-за похожего BPB.
4. `partition_priority` задаёт предпочтение MBR-разделов; `mount` обязан проверять всю используемую геометрию и границы. Никакого автоматического форматирования при ошибке.
5. Обязательны read-capability, mount/root/next/read/free. Для write-capability обязательны unlock/put/remove/rename. Версия, размер, неизвестные флаги, дубли ID/kind, отсутствующие операции проверяются до монтирования.
6. Добавьте исходник в `FS_DRIVERS`, объявление дескриптора в доступный заголовок и указатель в реестр. Один профиль — один набор модулей.
7. Проверяйте на образах, созданных независимым форматировщиком: корректные и испорченные структуры, отказы чтения/записи/flush, заполненный диск, границы и циклы. Для записи необходима проверка всех владельцев кластеров.

ABI сейчас рассчитан на одну смонтированную ФС, 32-битные адреса/размеры, 512-байтовые секторы. Это ограничение, а не поддержка всех современных накопителей/томов. Часть команд диагностики по-прежнему знает формат метаданных; интерфейс не является универсальным POSIX VFS.

## Установка готовых бинарников

Остановите ВМ, скопируйте образ, сохраните резервную копию.

```sh
python3 tools/imagectl.py install my-system.img --kernel build/kernel.bin --efi build/BOOTX64.EFI --boot build/boot.bin
```

Инструмент синхронизирует raw-копию BIOS-ядра с файлом `MULTIOS/KERNEL32.BIN` в ESP. Обычный файловый редактор этого не делает. Не меняйте только FAT-копию ядра вручную: BIOS читает raw-секторы.

`studio.py` тоже синхронизирует изменённый kernel32.bin и сохраняет ID диска/разметку при обновлении boot32.bin. Проверка формата бинарника не доказывает совместимость ABI или отсутствие ошибок внутри него.

## Простая внешняя структура против загрузочной разметки

Для новичка — `studio.py unpack`, обычные `files/`, `settings.ini`, `system/`. Внутри одного `.img` остаются raw-загрузочные секторы, FAT32 ESP с `EFI/BOOT/BOOTX64.EFI`, `MULTIOS/`, `DOCS/`, `SOURCES/`, `TOOLS/`, и отдельный DATA-раздел. Два раздела нужны для совместимой загрузки и выбора exFAT/FAT32/NTFS, это не два распространяемых образа. `START.TXT` в корне ESP объясняет начало; `DRIVERS.TXT` — где находятся исходники.

Исходники в `SOURCES/PORTING.ZIP` — снимок при создании образа. `unpack` экспортирует данные/настройки/готовые бинарники, не распаковывает этот ZIP автоматически. Полные исходники также лежат рядом с образом в архиве поставки.

## Что мешает полноценной NTFS

Чтение NTFS выполняется нашим freestanding C-кодом в BIOS и UEFI, без Linux/Windows. Но это ограниченный **RO backend**, не полноценная NTFS:

- нет записи MFT, allocation bitmap, дерева индексов I30 и согласованных изменений hardlink-метаданных;
- нет воспроизведения/обновления `$LogFile`, полноценной транзакционной/аварийной модели и восстановления после сбоя питания;
- нет полной поддержки `$ATTRIBUTE_LIST`, Unicode-сравнения через UpCase, ACL/security descriptors и всех named streams;
- каталоги перечисляются ограниченным сканированием MFT (не настоящий обход I30); ограничены число records/runs, размеры и адреса;
- compression, EFS, reparse, BitLocker и повреждённые/неподдерживаемые структуры не поддержаны полноценно.

Требуется отдельная большая реализация и независимая проверка совместимости, прежде чем разрешать запись на реальном NTFS. В этой версии дескриптор NTFS **не содержит write callbacks**, а VFS отказывает записи даже при ошибочно выставленном флаге writable. ntfs-3g применяется только в инструментах подготовки тестов на машине разработчика, не внутри ОС.
