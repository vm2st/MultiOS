# MultiOS 0.6-cpu: заменяемые драйверы и профили портов

> Текущий снимок: **0.11-dev, не опубликован**. Первая публичная версия — только
> стабильный **Release 1.0**. См. RELEASE_POLICY_RU.md и TWO_BUTTONS_RU.md.

**vm2 studios — t.me/v2vproj | MultiOS / MultiPulti.**

## Что изменилось

MultiOS остаётся консольной системой с общим кодом на C11. Ввод, вывод,
накопитель и питание теперь подключаются через отдельные драйверные дескрипторы.
UEFI и BIOS используют один менеджер модулей. Тестовый POSIX-harness тоже
собирает HAL этим способом, но не является загруженной самостоятельной ОС.

Это **статические C-модули с выбором при загрузке**, а не загрузчик ELF/DLL.
Нельзя положить произвольный `.sys` на флешку, выгрузить работающий драйвер или
установить драйвер Windows/Linux. Бинарники модулей отдельно от ядра пока не
загружаются. Модульный ABI 1 — контракт исходников для одной сборки/архитектуры;
это не стабильный межархитектурный формат бинарных файлов.

## 1. Самый простой вариант: поменять пару строк, без пересборки

На FAT32-флешке откройте `MULTIOS/BOOT.CFG`. Стандартный вариант:

```ini
output=uefi-text
input=uefi-keys
block=uefi-file
block.options=\MULTIOS\DATA.IMG
power=uefi-reset
osk=auto
```

Например, чтобы использовать упрощённую консоль без экранной клавиатуры:

```ini
output=uefi-plain
osk=off
```

Замените соответствующие строки, **не добавляйте вторые строки с тем же ключом**.
Остальные строки оставьте. Новые настройки действуют после перезагрузки.

Для жёсткого запрета записи замените только:

```ini
block=uefi-file-ro
```

Теперь `UNLOCK YES` не даст права записи: это запрет самого блочного провайдера.
Обычный `uefi-file` тоже начинает работу ФС в RO; RW требует явной разблокировки
и остаётся экспериментальным, без журналирования и гарантий при потере питания.

Для другого exFAT-образа на той же FAT32-флешке:

```ini
block.options=\MULTIOS\TEST.IMG
```

Укажите существующий образ с 512-байтными секторами. Файл не создаётся и не
форматируется автоматически. Меняется файл-образ, а не физический диск.

Для отказа от прошивочных вызовов выключения/перезагрузки:

```ini
power=uefi-no-reset
```

В этом режиме `POWEROFF` и `REBOOT` возвращают отсутствие поддержки,
а `EXIT` останавливает CPU, не выключая питание. Это полезно для диагностики,
но не исправляет прошивку и не реализует собственный ACPI-драйвер.

### Готовые UEFI-модули стандартной сборки

| Роль | ID | Возможности |
|---|---|---|
| Вывод | `uefi-text` | UEFI text 80×25, прокрутка, панель OSK |
| Вывод | `uefi-plain` | Простой прошивочный текстовый поток, без OSK |
| Ввод | `uefi-keys` | UEFI SimpleTextInput, символы, стрелки, F2 |
| Диск | `uefi-file` | Файл-образ через UEFI File I/O, RW capability при доступности |
| Диск | `uefi-file-ro` | Тот же формат образа, принудительный RO |
| Питание | `uefi-reset` | UEFI ResetSystem, предварительный flush |
| Питание | `uefi-no-reset` | Только остановка CPU |

`MODULES` показывает четыре реально выбранных провайдера. `DRIVERS` поясняет
границы аппаратной поддержки, `PLATFORM` — итоговый HAL и доступность записи.
Пока нет перечисления/автоподбора PCI/USB-устройств: профиль явно задаёт один
провайдер каждой роли и один том. Выбор роли не создаёт отсутствующий драйвер.

### Формат BOOT.CFG

- Обычный ASCII-файл, не более 2048 байт; LF или CRLF, регистр важен.
- Ключи: `output`, `input`, `block`, `power`, по одному на роль.
- Параметры: `output.options`, `input.options`, `block.options`, `power.options`.
- `osk=on`, `osk=off`, `osk=auto`; `auto` учитывает наличие `MULTIOS/OSK.ON`.
- ID до 39 символов, параметры до 127 символов, строка до 179 байт.
- Пустые строки, строки-комментарии `#`/`;`, пробелы вокруг `=` разрешены.
- Нет секций `[drivers]`, кавычек, подстановок и комментариев в конце значения.
- Все текущие драйверы, кроме файлового, принимают только пустые options.
- Если конфиг отсутствует, используются значения из реестра сборки.
- Неизвестный ключ, повтор ключа, отсутствующий модуль, несовпадение роли,
  неверные параметры или ошибка инициализации **останавливают загрузку**.
  Тихого переключения на другой диск/драйвер нет.
- `osk=on` с выходом без renderer — ошибка. При `auto` renderer может быть
  недоступен: система сообщает об этом, консоль продолжает работу без панели.

## 2. Замена реализации: один C-файл и регистрация

```text
shell / exFAT / OSK
        ↓
core/modules.c  → проверка профиля, ABI, запуск и rollback
        ↓
include/multios/modules.h   четыре интерфейса устройств
        ↓
drivers/<платформа>/*.c     самостоятельные реализации
        ↓
core/hal.c                 собранный HAL, границы LBA, RO/RW
```

Фактический вызов команд идёт shell → HAL → выбранные callbacks драйверов;
менеджер модулей собирает HAL один раз до монтирования ФС.

В `drivers/uefi/` находятся отдельные `text.c`, `plain.c`, `keys.c`, `file.c`,
`power.c`. В `drivers/pc-bios/` — `text.c`, `keys.c`, `ata.c`, `power.c`.
`platform/*` содержит startup/BSP, протокольное обнаружение и реестр, а не
реализацию файловой системы. BIOS COM1/PS2 и VGA/COM1 пока являются составными
провайдерами; здесь не вводится отдельная UART-шина или менеджер зависимостей.

При наличии готовой совместимой реализации:

1. Замените соответствующий C-файл, сохранив экспортируемый дескриптор; **или**
   добавьте свой файл и имя дескриптора в реестр платформы.
2. Для нового файла укажите его в `UEFI_DRIVERS`/`PC_DRIVERS` профиля `.mk`.
   Новый дескриптор должен быть объявлен в заголовке, доступном реестру.
3. Выберите ID в `BOOT.CFG` (UEFI) или compiled default profile (BIOS).
4. Пересоберите, протестируйте и замените `EFI/BOOT/BOOTX64.EFI` на флешке,
   предварительно сохранив предыдущую версию. BIOS требует пересборки образа.

Если реализация сохраняет путь исходника и имя дескриптора, достаточно заменить
один файл и пересобрать; конфиг не меняется. Если меняются ID/символы, понадобится
также регистрация. `lib/exfat.c` и `lib/shell.c` менять не нужно.

## 3. Профили сборки

Обычный вариант:

```bash
make usb
```

Готовый минимальный пример — другой набор исходников и другой реестр:

```bash
make usb UEFI_PROFILE=profiles/uefi-minimal.mk
```

Он исключает OSK-вывод `uefi-text` из линковки, выбирает `uefi-plain`,
`uefi-file-ro`, `osk=off`. `tools/mkusb.py` берёт соответствующий `UEFI_CONFIG`.
Это альтернативная сборка для той же x64 UEFI, **не порт на новую архитектуру**.

Вернуться к стандартному варианту:

```bash
make usb
```

Смена профиля отслеживается stamp-файлами, `make clean` между ними не нужен.
Результаты профилей используют общие пути `build/BOOTX64.EFI` и USB-образа:
предыдущая сборка заменяется. Не собирайте разные профили параллельно в одном
дереве. `make usb` генерирует `build/USB_FILES`; верхний `USB_FILES` — снимок
готовой поставки, при своей пересборке используйте именно `build/USB_FILES`.

Для своей платформы создайте собственные `.mk` и registry header:

```make
UEFI_DRIVERS = drivers/myboard/output.c drivers/myboard/input.c drivers/uefi/file.c drivers/uefi/power.c
UEFI_REGISTRY = ports/myboard/registry.h
UEFI_CONFIG = ports/myboard/BOOT.CFG
```

Это пример имён, файлов `myboard` в поставке нет. Аналогично BIOS:
`make PC_PROFILE=profiles/my-pc.mk`, поля `PC_DRIVERS`, `PC_REGISTRY`.
BIOS пока **не читает внешний BOOT.CFG** — его профиль компилируется в ядро.

## 4. Контракт нового драйвера

Заголовок: `include/multios/modules.h`. Каждый `MultiDriver` содержит ABI,
размер структуры, ID, роль, описание и `open`/необязательный `close`.
`MULTI_DRIVER(...)` задаёт актуальные ABI и размер. `open` получает BSP-context,
строку параметров и union для результата. Заполняйте только собственную роль.

- `MULTI_OUTPUT`: ctx, обязательный putc, необязательные clear/osk.
- `MULTI_INPUT`: отдельный ctx и getc, ASCII или события из `osk.h`, -1=EOF.
- `MULTI_BLOCK`: MultiBlock, ровно 512 байт на read/write; 0=успех,
  отрицательное число=ошибка. Writable требует настоящие write и flush.
- `MULTI_POWER`: ctx, обязательный stop, необязательные poweroff/reboot.

`open` не должен писать на диск. При собственной ошибке он сам освобождает
частично захваченные ресурсы. Если последующий модуль не запустился, менеджер
вызывает `close` ранее успешно открытых модулей в обратном порядке. Проверяются
реестр, уникальность ID и все роли до первого open. При успехе формируется HAL.
Никакой автоматической выгрузки после удачного запуска нет; callbacks и contexts
должны жить до конца работы. Поток один, интерфейс синхронный, heap не требуется.
Ошибочные callbacks не изолированы: нет процессов, sandbox или защиты памяти.
Драйвер остаётся привилегированным доверенным C-кодом, не безопасным плагином.

Шаблон подключения: `ports/module-template.c.in`. Он не входит в сборку и
требует настоящих `board_*` реализаций и startup/linker-кода. Старый
`ports/template.c.in` сохранён как пример прямого HAL.

Для кнопок без клавиатуры ваш input-драйвер должен выдавать
`MULTI_KEY_UP/DOWN/LEFT/RIGHT` и Enter. Общая OSK уже умеет это обрабатывать,
но GPIO, gamepad или touchscreen сами собой от настройки не появятся.

## 5. Что нельзя решить заменой строк

Новая ISA (ARM/RISC-V), другой загрузочный протокол, MMU, исключения, DMA,
другой сектор, USB-host, NVMe, контроллер SD/eMMC — это реальная разработка
startup/BSP/драйверов. Готового универсального драйвера для всех устройств нет.
Для уже поддержанного boot environment модуль уменьшает объём интеграции,
а не отменяет написание аппаратного кода. Подробности — `PORTING_RU.md`.

UEFI-вариант по-прежнему использует Boot Services и драйверы прошивки.
Модульность не превратила его в native post-ExitBootServices ядро. Сборка и
загрузка проверены в QEMU; физических устройств в этой работе не тестировали.

Последняя команда только компилирует portable-core объекты для ARMv7/AArch64/

обычные build-файлы и тестовые образы, не физические диски.

## 7. Обновление флешки 0.3 → 0.4

Сначала сохраните резервную копию всей флешки, особенно `MULTIOS/DATA.IMG`.
Для стандартной сборки замените `EFI/BOOT/BOOTX64.EFI` и добавьте
`MULTIOS/BOOT.CFG` из **того же** комплекта сборки. Формат exFAT-образа не менялся;
если в вашем DATA.IMG уже есть файлы, не заменяйте его пустым образом поставки.
Не обновляйте загруженную систему: выключите её, обновите файлы с другого
компьютера, безопасно извлеките накопитель и загрузитесь заново. Не перезаписывайте
чужой UEFI-loader: эти шаги только для вашей флешки MultiOS.


## MultiPulti и единый образ (0.5)

Автор шаблона: vm2 studios — t.me/v2vproj. Основная поставка теперь описана в
`ONE_IMAGE_RU.md` / `MULTIPULTI_RU.md`. В её BOOT.CFG по умолчанию выбран
`uefi-boot-disk`, который через прошивочный Block I/O открывает **именно диск
загрузочного раздела** и общий exFAT-раздел. Альтернатива — `uefi-boot-disk-ro`.
Эти два модуля добавлены в standard registry, но отсутствуют в учебном
`uefi-minimal` file-backed профиле. В unified-образе DATA.IMG отсутствует;
не меняйте block на uefi-file, если вы не подготовили такой файл отдельно.

Самостоятельное BIOS-ядро называется MultiPulti32; UEFI target по-прежнему
firmware-hosted, не самостоятельное post-firmware x64-ядро. Внешние бинарные
драйверы на лету всё ещё не загружаются: образ редактируется снаружи и запускается
заново. Новый источник драйвера надо скомпилировать, затем обновить bundle.
