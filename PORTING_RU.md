# MultiOS 0.6-cpu: перенос на новые устройства

> Текущий снимок: **0.11-dev, не опубликован**. Первая публичная версия — только
> стабильный **Release 1.0**. См. RELEASE_POLICY_RU.md и TWO_BUTTONS_RU.md.

**vm2 studios — t.me/v2vproj | MultiOS / MultiPulti.**

Графическая ветка и графический установщик отменены. Добавлена текстовая OSK и дополнительный x64 UEFI live target с firmware services, см. USB_RU.md. Основная система остаётся консольной, на C11. Этот выпуск отделяет аппаратно-зависимый код от exFAT и команд, но **не объявляет ARM/RISC-V уже поддержанными загрузочными платформами**.

В 0.4 добавлен менеджер модулей (`core/modules.c`), отдельные `drivers/uefi/` и
`drivers/pc-bios/`, профили `.mk` и UEFI BOOT.CFG. Основная инструкция нового
способа подключения — `MODULES_RU.md`; описание прямого HAL ниже сохраняется
как низкоуровневый контракт и для старых интеграций.

## 1. Границы слоёв

```text
lib/shell.c             команды и разбор строк
lib/exfat.c             exFAT, работа с сырыми байтами секторов
lib/util.c              небольшие независимые утилиты
          ↓
include/multios/hal.h   контракт консоли и блочного устройства
core/hal.c             проверка контракта, границ I/O, RO/RW, адаптация API
          ↓
platform/pc-bios/       собственная загрузка x86, VGA/PS2/serial/IDE
platform/uefi/          UEFI live environment, Boot Services активны
platform/posix/         тестовая программа Linux/POSIX; не самостоятельная ОС
```

Общий код не содержит inline assembly, портового I/O, адреса VGA или вызовов POSIX. Для freestanding-части используются стандартные точные типы `uint8_t`, `uint16_t`, `uint32_t`, а не предположение, что `unsigned int` всегда 32-битный. Числа exFAT декодируются из little-endian байтов явно; нельзя заменять это кастами к packed structs.

## 2. Что должен дать каждый порт

### Консоль

- `putc(ctx, ch)` — вывести один ASCII-байт. Реализация: UART, USB CDC, VGA или другая текстовая консоль.
- `getc(ctx)` — дождаться байта, вернуть 0..255 либо -1 при EOF.
- `clear(ctx)` — необязательный сброс экрана; для простого UART можно не задавать.

Код shell сейчас обрабатывает ASCII и LF/CR, Backspace, Ctrl+C. Терминальные escape sequences, Unicode и полноценная line discipline не абстрагированы отдельно.

### Блочное устройство

- `read(ctx, lba, buffer)` — прочитать ровно один 512-байтный логический сектор.
- `write(ctx, lba, buffer)` — записать ровно один сектор; отсутствует для read-only порта.
- `flush(ctx)` — дождаться устойчивой записи всех предыдущих изменений; обязателен для RW.
- `sectors` — число доступных логических секторов, проверенное вашим драйвером.
- `sector_bytes = 512` — текущее подмножество драйвера exFAT.
- Возврат read/write/flush: **0** при полном успехе, отрицательная ошибка при неуспехе. Возвращать число байтов вместо 0 нельзя.

Слой устройства может представлять ATA, SD/eMMC, virtio или файл в тестовой программе. 4Kn-устройство требует корректного read-modify-write/flush-адаптера либо расширения всей ФС на больший сектор — просто объявить его сектор 512 байт нельзя.

### Загрузка и завершение

Порт отвечает за entry point, стек, очистку BSS, память, linker script, ABI вызова C, обязательную инициализацию платы и обработку аппаратных исключений. `stop(ctx)` останавливает/перезагружает устройство или возвращается в тестовый harness. Нынешний PC-порт останавливает CPU, не реализует универсальное выключение питания.

## 3. Подключение

До первого вызова `shell()` создайте `MultiHal`, задайте `abi = MULTIOS_HAL_ABI`, имя/архитектуру, callbacks консоли и диска, затем вызовите `multi_hal_bind(&hal)` и проверьте результат.

При успешном bind дескриптор копируется, но память, на которую указывают `ctx` и строки, должна оставаться доступной до завершения работы. Подключение другого устройства при уже смонтированной ФС запрещено. Незаметное переключение дисков недопустимо.

Пример входной точки находится в `ports/template.c.in`: это **шаблон интеграции**, а не работающий ARM/RISC-V BSP. Он не входит в сборку и требует ваших драйверов и startup-кода.

## 4. Рабочая последовательность переноса

1. Выберите конкретную плату/эмулятор: например, QEMU `virt` AArch64 или QEMU RISC-V `virt`. «Все ARM» — не одна аппаратная платформа.
2. Реализуйте startup и serial `putc/getc`, добейтесь строки `MultiOS: board ready`.
3. Добавьте read-only блочное устройство; проверьте LBA 0 и границы, запретите DMA за пределы буферов.
4. Привяжите HAL, соберите `core/hal.c`, `lib/util.c`, `lib/exfat.c`, `lib/shell.c` без изменений под выбранный target.
5. Подключите compiler runtime для вашего ABI: ARM может требовать `__aeabi_*`, а компилятор — helpers деления, memcpy/memset. Не считайте успешную компиляцию `.o` успешной линковкой или загрузкой.
6. На одноразовом exFAT-образе проверьте DIR/TYPE/CRC32 и совпадение данных с хостом.
7. Только после проверки read-only, ошибок I/O, границ, кэшей и flush включайте RW. Ни одна заглушка flush, возвращающая 0 без реального сохранения, недопустима.
8. Повторите файловые тесты, независимый fsck и fault-injection на своей платформе. На физическую плату переносите после проверок в эмуляторе.

## 5. Инструменты проверки

```bash
make test-hal       # контракт HAL на in-memory устройстве
make check-core     # статическая граница portable/platform
make                # загрузочный x86 и POSIX harness
QEMU=/path/to/qemu-system-x86_64 make test
```

Дополнительная compile-only проверка независимых файлов для ARMv7, AArch64 и RISC-V64 при установленном clang:

```bash
python3 tests/cross_compile.py
```

Она создаёт **только object files**. Это не готовые загрузочные образы, не эмуляция CPU и не доказательство корректности драйверов. Результаты текущего выпуска перечислены в TESTING_RU.md.

## 6. Нынешние границы переносимости

- Один том, глобальный объект `vol`, один поток; код не реентрантен и не thread-safe.
- Процессоры с 8-битным байтом и стандартными 8/16/32-битными точными типами.
- Синхронное I/O, без async/DMA API и без аллокатора ядра.
- В HAL и текущей ФС сохраняется консервативный предел 128 GiB, 32-битные LBA/длины, сектор 512 байт; файлы меньше 4 GiB.
- Нет VFS, scheduler, процессов, системных вызовов и загрузчика пользовательских программ.
- BIOS-бинарник — x86 32-bit; отдельно поставляется x64 UEFI live environment. ARM/RISC-V BSP пока нет.
- Linux/POSIX адаптер — тестовая программа поверх другой ОС. Самостоятельность обеспечивается только bare-metal портом.

## 7. Команда PLATFORM

`PLATFORM` (псевдоним `HAL`) показывает реально подключённые имя платформы, архитектуру, версию HAL, размер/число секторов и возможность записи. `VER` больше не выдаёт host-harness за уже загруженное protected-mode ядро.

Дальнейший полезный шаг — выбрать **одну конкретную** вторую платформу и довести её до загрузки, не обещая универсальный образ для всех устройств.

## HAL ABI 2: события ввода и питание

`MultiConsole.getc` теперь может возвращать MULTI_KEY_UP/DOWN/LEFT/RIGHT/OSK из multios/osk.h. Общий слой преобразует навигацию OSK в символы. `console.osk` отображает состояние панели; без renderer включение OSK отклоняется. Для кнопок платы нужен реальный драйвер, формирующий эти события. Поля lifecycle `poweroff` и `reboot` необязательны; отсутствие означает UNSUP, а не фиктивный успех. Поле `drivers` — диагностическая строка реализованных возможностей. ABI повышен до 2; старые бинарные дескрипторы ABI 1 не принимаются.
